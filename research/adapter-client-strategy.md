# Research: reuse vs write the OpenRouter adapter client

Ticket: [Research: reuse vs write the OpenRouter adapter client](https://github.com/mgschiebel/libharness/issues/29)
Researched: 2026-11-01

**Question.** For the optional OpenRouter adapter (the std-side piece, outside the no-I/O core, that implements the model-call capability the host registers), should libharness reuse an existing Rust client crate (genai, async-openai, or another) or write its own small client? Evidence only: licence, dependency weight, runtime coupling, OpenRouter streaming fidelity, OpenRouter-specific fields, release stability, and how each would sit behind a host-registered model-call capability. This file does not recommend.

Out of scope (separate grilling): where the adapter lives in the crate layout. Settled and not re-opened: [ADR 0001](https://github.com/mgschiebel/libharness/blob/main/docs/adr/0001-build-the-core-from-scratch.md) (no provider client in the core; concepts only, no copied code).

## 2. Licence

- All five candidate crates and the HTTP/SSE building blocks are permissive: genai MIT OR Apache-2.0 (both licence files present: [LICENSE-MIT](https://docs.rs/crate/genai/0.7.2/source/LICENSE-MIT), [LICENSE-APACHE](https://docs.rs/crate/genai/0.7.2/source/LICENSE-APACHE)); async-openai MIT; openrouter-rs MIT ([LICENSE](https://docs.rs/crate/openrouter-rs/0.23.0/source/LICENSE)); openrouter_api MIT OR Apache-2.0; reqwest and ureq MIT OR Apache-2.0; eventsource-stream MIT OR Apache-2.0 (Cargo.toml `license` fields, crates.io API above) **[Read]**. The async-openai package on crates.io contains no licence file (only the SPDX field); the repository does ([landscape note](https://github.com/mgschiebel/libharness/blob/main/research/rust-llm-landscape.md)).
- **Transitive licences [Tested].** Every tree that includes a TLS stack (genai, async-openai, openrouter-rs, reqwest+rustls, even ureq's default) contains licences beyond "MIT/Apache": ISC (`rustls-webpki`, `untrusted`, `ring` is `Apache-2.0 AND ISC`, `aws-lc-rs` is `ISC AND (Apache-2.0 OR ISC)`), BSD-3-Clause (`subtle`), Zlib (`foldhash`), Unicode-3.0 (the `icu_*` family in genai's tree), and CDLA-Permissive-2.0 (`webpki-roots` / `webpki-root-certs`, a data licence for the certificate bundle). One crate offers `MIT OR Apache-2.0 OR LGPL-2.1-or-later`, which is a choice, not an obligation. ureq without TLS contained none of these extras in the check run (reqwest without TLS was not checked).
- **[Inference]** ADR 0001 limits licences for *core* dependencies, and the adapter is outside the core. If the cargo-deny licence allow-list is later applied to the adapter as well, it would need ISC, Unicode-3.0, Zlib and CDLA-Permissive-2.0 entries for any TLS-bearing option. A host-supplied transport would avoid the question.

## 4. OpenRouter streaming fidelity

### 4.1 What the wire format is (primary)

From [O1], the Chat Completions streaming schemas (all names verbatim):

- `ChatStreamChunk` properties: `alignment`, `choices`, `created`, `error`, `id`, `model`, `object` (`chat.completion.chunk`), `openrouter_metadata`, `safeguard_results`, `service_tier`, `system_fingerprint`, `usage`.
- `ChatStreamChunk.error` is `{ code: integer (int32), message: string, metadata?: { error_type: ApiErrorType (required), provider_code?: string } }`, with `code` and `message` required. `ApiErrorType` has 27 values (for example `rate_limit_exceeded`, `context_length_exceeded`, `provider_overloaded`, `server`, `timeout`, `unmapped`) and allows unknown values.
- `ChatStreamChoice` requires `delta`, `finish_reason`, `index`; optional `logprobs`. `ChatFinishReasonEnum` is `tool_calls`, `stop`, `length`, `content_filter`, `error`, `null`, with unknown values allowed.
- `ChatStreamDelta` properties: `audio`, `content` (string or null), `reasoning` (string or null, "Reasoning content delta"), `reasoning_details`, `refusal`, `role` (`assistant`), `tool_calls`.
- **Tool-call deltas (the format flagged UNKNOWN in [research/openrouter-api.md](https://github.com/mgschiebel/libharness/blob/main/research/openrouter-api.md), now verified).** `ChatStreamDelta.tool_calls` is an array of `ChatStreamToolCall`, described as "Tool call delta for streaming responses": `index` (integer, the only **required** field, "Tool call index in the array"), optional `id`, optional `type` (`function`), optional `function` with optional `name` and optional `arguments` ("Function arguments as JSON string"). The schema's example puts `id`, `name` and a complete `arguments` string together in one delta.
- The streaming tutorial [O3] says "When you stream a response, tool calls arrive in pieces called deltas. The model may split the arguments string across chunks and build the tool_calls array one index at a time. Don't run the tool before the stream ends. Collect the deltas by index, wait for the finish signal, parse the complete arguments string, and then execute."
- The tool-calling guide [O4] shows streaming only for the Responses API.
- `ChatStreamOptions.include_usage` is deprecated: "This field has no effect. Full usage details are always included."
- `ChatUsage` has `prompt_tokens`, `completion_tokens`, `total_tokens`, `prompt_tokens_details` (`cached_tokens`, `cache_write_tokens`, `audio_tokens`, `video_tokens`), `completion_tokens_details` (`reasoning_tokens` and others), `cost` ("Cost of the completion", number or null), `cost_details`, `is_byok`, `server_tool_use_details`. The unit of `cost` on this schema is **not stated**; other schemas in the same spec say "Cost of the request in credits" (embeddings and rerank usage), and `cost_details.server_tool_cost` is stated in USD.
- [O2] (also in the earlier research): SSE comment lines such as `: OPENROUTER PROCESSING` appear and must be skipped; after the `200` is sent, a Chat Completions failure arrives as a final chunk with a top-level `error` and a `choices` entry with `"finish_reason":"error"`; a `200` with only an error event is a failure; the usage chunk before `[DONE]` carries one content-free choice repeating `finish_reason`.
- The SSE grammar those rules sit on is [W1]: lines starting with `:` are ignored; `data` lines accumulate with a trailing line feed; a blank line dispatches; incomplete events at end of stream are discarded; CR, LF and CRLF all end lines; one leading BOM is stripped.
- **Still [Unknown]:** how each upstream provider fragments tool calls in practice (the schema makes `id` and `name` optional on every delta; the tutorial says arguments may split across chunks; nothing observed). Whether fragments of different `index` values interleave. The chunk shape when `finish_reason` is `error` and also `choices` is empty.

## 5. OpenRouter-specific request and response fields

[O1] `ChatRequest` has 43 properties, including the OpenRouter-only `models`, `route`, `provider`, `plugins`, `reasoning`, `session_id`, `trace`, `metadata`, `cache_control`, `prompt_cache_key`, `service_tier`, `stop_server_tools_when`, `deferred_tools`. Only `messages` is required. The `provider` object (`ProviderPreferences`) is closed (`additionalProperties: false`). Unknown extra parameters are ignored by OpenRouter, so a typo in an unchecked field fails silently ([research/openrouter-api.md](https://github.com/mgschiebel/libharness/blob/main/research/openrouter-api.md)).

## 6. Release stability and maintenance

- **genai.** Pre-1.0 and says so. 0.7.0 (2026-10-19) was breaking in several places: `Client::new()` became fallible, `ReasoningEffort::None` was renamed, a schema helper was removed, and the JSON serialisation of its types changed ([CHANGELOG](https://docs.rs/crate/genai/0.7.2/source/CHANGELOG.md)). Every new provider adds an `AdapterKind` variant that the changelog flags as breaking for exhaustive matches (0.7.1 entries for `cloudgpu::` and `runcrate::`). The packaged changelog still heads 0.7.1 as "pending" while 0.7.2 is on crates.io (2026-10-28). Two 0.5.0 alphas were yanked. OpenRouter-specific work is community-driven and recent (OpenRouter adapter PR 230; `reasoning_details` capture PR 301; streaming follow-up PR 360 open). A tool-call correctness question ([issue 322](https://github.com/jeremychone/rust-genai/issues/322)) sat unanswered; the 0.7.1 changelog entry for PR 347 ("Keep every piece of a streamed chunk", by a contributor) covers the same two gaps the issue asks about **[Inference]**. Open-issue counts **[Unknown]**.
- **async-openai.** Highest adoption by far (about 3.2 million recent downloads), declared MSRV 1.75, and the stated scope is "official OpenAI APIs": a maintainer replied to an OpenRouter deserialisation failure by pointing at `byot` with `serde_json::Value` ([issue 503](https://github.com/64bit/async-openai/issues/503); the page shows no date or state, **[Unknown]**). 13 minor versions in 12 months, 0.31 to 0.43, so 0.x minors are frequent. A changelog file was not located in the repo or the package ([landscape note](https://github.com/mgschiebel/libharness/blob/main/research/rust-llm-landscape.md)), so what breaks per release was not measured.
- **openrouter-rs.** The fastest-moving: 0.10.0 (2026-05-20) to 0.23.0 (2026-10-30) is 13 minor releases in about five months, and the CHANGELOG has 18 lines mentioning "Breaking". 0.23.0 alone removed 162 free endpoint functions and 109 flat client methods, removed `ToolAwareStream`/`StreamEvent` in favour of `stream_unified`, and renamed management endpoints after an "upstream drift review". The README's release notes say the MSRV was raised to 1.93 together with the 0.21 backend-feature change ([README](https://docs.rs/crate/openrouter-rs/0.23.0/source/README.md)). The repo documents a [maintenance policy](https://docs.rs/crate/openrouter-rs/0.23.0/source/docs/policies/maintenance-policy.md) and a compatibility-update policy, and marks high-churn types `#[non_exhaustive]`. Most of its surface (management, analytics, SCIM, guardrails) is irrelevant to a model-call adapter. The README calls it "community-maintained"; bus factor was not measured.
- **openrouter_api.** 15 versions since 2025-02, last release 2026-08-12, low recent downloads (353). A content-`null` deserialisation bug on tool-call responses was reported in May 2026 and fixed in August ([issue 65](https://github.com/socrates8300/openrouter_api/issues/65)) (the page describes `content: null` on assistant messages that carry tool calls). Uses reqwest 0.12 while the others use 0.13.
- **Own client.** No upstream churn to track, but OpenRouter's own API drifts: the spec is a single 2.7 MB file [O1], and openrouter-rs spent a changelog entry on an "upstream drift review" in 0.23.0. The chat-completions streaming slice a model-call adapter needs is a small fraction of that spec (the `ChatStreamChunk` schema has 12 properties). **[Inference]** drift in the slice is detectable by diffing the spec. No source measures how often that slice changes.

## 7. How each sits behind a host-registered model-call capability

Fixed on the libharness side: under session-as-task the model call is a boxed `Send + Sync + 'static` callback taking a request and returning a reply (or error) ([session-as-task](https://github.com/mgschiebel/libharness/issues/19), [map notes](https://github.com/mgschiebel/libharness/issues/1)). Prototype #7 found the callback's `Result<_, String>` error type, not the provider trait, is the real constraint: it cannot carry retry hints, partial output or cost ([README, Surprises](https://github.com/mgschiebel/libharness/blob/prototype/provider-abstraction/prototypes/provider-abstraction/README.md)).

**Common to any reuse option [Inference from the sources in sections 3 to 5]:**

- *Translate in:* the library's request (messages, tool declarations as JSON schema, options) becomes the crate's request types; the host's credential goes into the crate's auth hook (genai `AuthResolver`, openrouter-rs client builder, async-openai `Config`).
- *Translate out:* the crate's response or stream events become the library's reply (text, tool calls, finish reason, usage, served model, error). Each crate has its own error enum (`#[non_exhaustive]` for openrouter-rs) that flattens to the callback's error type.
- *What leaks:* a tokio runtime requirement; a pinned reqwest major (0.13 for genai, async-openai, openrouter-rs; 0.12 for openrouter_api) that also appears in the host's tree whenever the host passes its own `reqwest::Client` (genai `with_reqwest`, async-openai `with_http_client`, openrouter-rs `http_client`); TLS and build-script weight; and the crate's semver cadence into the adapter's public surface.

**genai.** One client, model selected by `open_router::<id>` namespace; chat and chat-stream calls return a response or a stream of `Start`, `Chunk`, `ReasoningChunk`, `ThoughtSignatureChunk`, `ToolCallChunk`, `End`, `Heartbeat` events, with `StreamEnd` capturing usage, stop reason, content and response id ([chat_stream.rs](https://docs.rs/crate/genai/0.7.2/source/src/chat/chat_stream.rs)). Translation is richest here because its message model is provider-neutral. Leaks: `cost` and OpenRouter routing fields need `extra_body` JSON and a side channel the typed usage does not carry; its adapter and codec layer is private (`mod adapter_types;` is not exported, [adapter/mod.rs](https://docs.rs/crate/genai/0.7.2/source/src/adapter/mod.rs)), so only the whole client can be reused, not the OpenRouter codec; its README lists dozens of other provider adapters that ride along.

**openrouter-rs.** OpenRouter-native types for request, response and usage, including `cost`, `provider`, `models`, `plugins`. A unified stream event model (`ContentDelta`, `ReasoningDelta`, `ReasoningDetailsDelta`, `ToolDelta`, `Done` with assembled tool calls, `Error`) across Chat, Responses and Messages ([README](https://docs.rs/crate/openrouter-rs/0.23.0/source/README.md), [CHANGELOG](https://docs.rs/crate/openrouter-rs/0.23.0/source/CHANGELOG.md)). Translation is thinnest here. Leaks: the highest churn of the options (section 6), MSRV 1.93, a very wide public surface of which the adapter uses a few calls, and a community-maintained project.

**async-openai.** Typed OpenAI request and response; OpenRouter fields come through `byot` (own serde types) on its HTTP and SSE plumbing, with `Config` setting base URL and headers ([README](https://docs.rs/crate/async-openai/0.43.0/source/README.md)). With `byot` the adapter owns the OpenRouter codec and borrows only HTTP, SSE framing, retry/tower middleware and configuration. Leaks: the typed path cannot represent OpenRouter's `finish_reason: error` (section 4.2) or `cost`; mid-stream error recognition would have to be added in the adapter either way; scope statement says OpenAI only.

**Own client.** The library-side contract stays as small as the prototype's: a pure codec turning bytes into stream events and an assembler folding them into the reply, plus a transport seam. Translation in and out is the adapter's own code against the spec [O1]. What the prototype measured: OpenRouter codec 222 lines, SSE parser 72, assembler 98, types 150, driver and callback plus transport traits 75, 14 tests; codec builds `no_std` + `alloc` ([README](https://github.com/mgschiebel/libharness/blob/prototype/provider-abstraction/prototypes/provider-abstraction/README.md)). What remains to be built or chosen: the real HTTP transport (the options and weights are in section 3), TLS and proxy handling (host's, or a dependency), retry and backoff (needs a timer; no timer capability exists in the library, per the session-as-task findings), and whatever OpenRouter adds to the chat-completions slice. Leaks: error detail beyond eight normalised kinds survives only in opaque metadata; provider options are unchecked JSON; reasoning fields are dropped unless added.

## 8. Facts a decision turns on, and what is still unverified

- **Verified now:** the streaming tool-call delta format [O1] (index required; id, name, argument fragments optional). The in-stream error object and its typed `error_type` [O1].
- **Established by source reading, not by running:** which candidates skip comment lines, recognise in-stream errors and assemble tool calls (table 4.2). No candidate has been run against an OpenRouter-shaped stream.
- **Unverified and worth a prototype:** whether each reuse option, pointed at a local mock server replaying the OpenRouter fixtures, recovers partial text on a mid-stream error, folds interleaved tool-call deltas, surfaces `cost` and the served model, and closes the connection on drop; the cost in lines and dependencies of an own client with a real transport; whether a tokio runtime inside the adapter coexists with a runtime-neutral session loop on a non-tokio executor.
- **Unknown, not resolvable here:** live-API behaviour of any option (no key); real per-provider tool-call fragmenting; unit of `usage.cost` on chat completions [O1]; GitHub-side maintenance signals (last commit, open-issue counts, bus factor) for all five crates; whether openrouter-rs's `wasip3` backend works on a native host; openrouter-rs 0.23.0's behaviour on tool calls missing `id` or `name`; genai's handling of OpenRouter's usage-chunk shape; the async-openai changelog; the rest of the crates in section 1 "not examined".
